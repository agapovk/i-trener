# Development Workflow

## Подход

Строй проект инкрементально, по spec-driven подходу. Context-файлы определяют что строить, как строить и каков текущий прогресс. Всегда имплементируй по этим спекам — не изобретай поведение с нуля.

---

## Правила скоупинга

- Работай над одним feature-слайсом или подсистемой за раз.
- Предпочитай маленькие, проверяемые инкременты масштабным изменениям.
- Не объединяй несвязанные FSD-слои или слайсы в одном шаге.

---

## Когда разбивать задачу

Разбивай шаг имплементации, если он объединяет:

- Изменения в более чем двух FSD-слоях одновременно
- Изменения UI и контентной модели
- Несколько несвязанных компонентов или типов контента
- Поведение, которое не определено в context-файлах

Если изменение нельзя быстро проверить end-to-end — скоуп слишком широк, разбивай.

---

## Работа с отсутствующими требованиями

- Не придумывай продуктовое поведение, не определённое в context-файлах.
- Если требование неоднозначно — уточни его в соответствующем context-файле до имплементации.
- Если требование отсутствует — добавь его как открытый вопрос в `progress-tracker.md`.

---

## Синхронизация документации

Обновляй соответствующий context-файл при изменении имплементации:

- Системная архитектура, FSD-структура → `architecture-context.md`
- Контентная модель (frontmatter-схема) → `architecture-context.md`
- UI-токены, layout-паттерны, компонентные соглашения → `ui-context.md`
- Кодовые соглашения, инструментарий → `code-standards.md`
- Скоуп фич → `project-overview.md`

Состояние прогресса должно отражать фактическое состояние, а не запланированное.

## Git Workflow

### Ветки

- `main` — защищена. Все изменения — через pull requests.
- Создавай ветку перед началом любой имплементации.
- Именование: `<type>/<short-description>`

| Тип | Когда использовать |
|-----|--------------------|
| `feat/` | Новая фича или слайс |
| `fix/` | Исправление бага |
| `refactor/` | Рефакторинг без изменения поведения |
| `chore/` | Инструментарий, конфиг, зависимости |
| `docs/` | Обновление context-файлов или документации |
| `content/` | Добавление или обновление MDX-контента |

Примеры: `feat/material-list`, `fix/mdx-slug-parsing`, `content/interview-sidorov`

### Формат коммитов

Каждый коммит должен следовать **Conventional Commits**:

```
<type>(<scope>): <short description>
```

- Type: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `style`, `content`
- Scope: FSD-слайс или подсистема (опционально, рекомендуется)
- Description: строчные, imperative, без точки на конце

```bash
# Хорошо
feat(material): add material list page with category filter
fix(mdx): handle missing image frontmatter field
chore: configure biome and pnpm scripts
content: add interview with Sidorov
docs: update architecture-context with resume routes

# Плохо
Added material page
fix bug
WIP
```

AI должен предложить commit message перед коммитом и подтвердить формат.

### Pull Requests

- Один PR на фича-единицу или исправление.
- Заголовок PR — в том же формате Conventional Commits.
- Описание PR: что изменилось, какие context-файлы обновлены, как проверить.

### Git-ответственность AI

AI должен:

1. Предложить имя ветки перед началом имплементации.
2. Писать commit messages в формате Conventional Commits.
3. Никогда не пушить напрямую в `main`.
4. Указывать, если коммит смешивает несвязанные задачи — вместо этого разбить.

---

## Перед переходом к следующей единице

1. Текущая единица работает end-to-end в рамках своего скоупа.
2. Ни один инвариант из `architecture-context.md` не нарушен.
3. `pnpm check` и `pnpm typecheck` проходят без ошибок.
4. `pnpm build` завершается без ошибок.
5. Все изменения закоммичены в правильном формате.
6. Pull request открыт для завершённой ветки.
7. `progress-tracker.md` отражает завершённую работу.
